# Markdown 知识库规范

本文档规定第四阶段整理正式 Markdown 知识时的内容边界和维护方式。它约束知识提案与审核结果，不要求改造用户已经存在且结构合理的文档。

## 仓库边界

- 工具仓库保存 Skill、脚本、契约和合成测试数据；正式知识库默认位于另一个由用户显式指定的根目录。
- 知识库只把获批 Markdown、必要目录说明和最小应用审计作为正式内容。
- 原始对话、标准化文件、知识候选、inventory、检索结果、审核包、diff 和 after 文件是私密运行数据，不进入正式知识历史。
- 当前流程不建立 SQLite、向量数据库或其他持久化检索索引。检索所需目录可以随时从 Markdown 重新生成。

## 最小充分上下文

正式知识应足以支持以后理解、判断或执行，但不保存生成结论的完整对话。整理时遵循：

- 保留结论、适用条件、必要理由、操作步骤和容易误用的边界。
- 删除寒暄、重复论述、推导过程、面向当前对话的措辞和不影响复用的背景。
- 不直接复制 assistant 的长回答；先核对证据，再重写为与现有文档一致的知识表达。
- 示例只有在帮助执行、区分相近概念或防止误用时才保留。
- 无法确认真实性、时效性或适用范围的内容不得伪装成确定知识，应标记冲突或暂缓。

不使用统一字数上限。内容是否保留取决于复用价值和必要语境，而不是回答原本有多长。

## 推荐的分层结构

新建主题文档时，可以按实际需要使用以下层次，不要求每篇文档机械包含全部标题：

```markdown
# 主题名称

用几句话说明本文解决的问题和适用范围。

## 核心结论

- 最重要、可快速回忆的结论、决定或约束。

## 使用方法

可执行的步骤、命令或判断方式。

## 边界与注意事项

适用条件、例外、风险和容易踩坑的地方。

## 补充说明

只有确实有助于理解或以后使用的细节。
```

现有知识库有明确风格时优先延续现有结构。Frontmatter 第一版保持可选；不得为了符合模板而批量重写无关文档。

## 融合与拆分

- 已有等价结论时使用 `no_change`，不重复添加。
- 已有相关章节时优先 `merge`，避免创建“补充版”“最终版”或带数据格式版本号的知识文档。
- 新内容形成可独立检索、独立维护且边界清晰的主题时，才考虑新建文档。
- 文档变长本身不是拆分理由；主题职责混杂或维护周期明显不同时才拆分。
- 冲突内容并列展示各自来源和不确定性，等待用户决定，不静默选择更新、更长或措辞更肯定的一方。

## 文件与 Git

- 文档路径使用知识库根目录下的相对路径，文件名表达稳定主题，不包含 `v2`、`final`、日期等内容版本标记。
- 数据格式版本写入 JSON `format`；知识内容的历史由 Git 管理，不在文件名中复制版本。
- Skill 可以在应用后帮助检查 `git status`、`git diff` 和 `git diff --check`，但没有单独授权时不得暂存、提交或推送。
- 一个 Git 提交应对应一个可说明的知识主题或审核批次，避免逐句提交，也避免把大量无关主题积压成一个提交。

知识库若使用 `.knowledge-curator/` 保存本地运行数据，建议至少忽略：

```gitignore
.knowledge-curator/runs/
.knowledge-curator/reviews/
.knowledge-curator/cache/
```

需要版本管理的最小应用审计可以单独放在 `.knowledge-curator/audit/`，不要被上述宽泛规则一并忽略。
